# Возрастные/гендерные категории в TT Tournament Manager (`tournament/*.gs`)

Дата: 2026-08-25. Проект — отдельный Google Apps Script («TT Tournament
Manager», `tournament/*.gs`), не связан с Django-частью Pingo. Весь
`tournament/` (включая эту спеку, `tournament/docs/`) вне git —
`.gitignore` репозитория Pingo его не отслеживает, документ живёт только
локально.

## Контекст и проблема

Сейчас движок жеребьёвки/матчей (`Draw.gs`, `Matches.gs`) работает с
единым плоским списком участников: один посев, одна сетка групп/плей-офф,
один протокол. Организатору нужно уметь проводить турнир, где дети,
подростки и взрослые (и внутри них — мужчины/женщины) играют в отдельных
сетках параллельно, в рамках одного мероприятия и общего пула столов.

На реальных данных (19 участников из диалога с пользователем, возраст на
25.08.2026): дети (≤12) — 3 чел., подростки (13-17) — 2 чел., взрослые
(18+) — 14 чел. При делении ещё и по полу часть из 6 корзин
(возраст×пол) останется по 0-2 человека — отдельная сетка для 1-2 человек
бессмысленна. Отсюда — обязательное автослияние малых категорий.

## Область изменений

Затрагиваются: `config.gs`, `wizard.gs`, `participants.gs`, `forms.gs`,
`setup.gs`, `draw.gs`, `matches.gs`, `reports.gs`, `teams.gs` (парные
турниры — категория участника пары берётся по первому игроку, пол пары
не проверяется на совпадение); плюс новый файл `categories.gs`.

## 1. Данные

### Лист «Участники» — новые колонки
Добавляются в конец текущего списка из 16 колонок (`Setup.initParticipants`):
- **«Пол»** — значения `"Мужской"` / `"Женский"`, заполняется из формы/Excel-импорта/тестовых данных.
- **«Категория»** — текстовая метка, заполняется автоматически на шаге
  «Посев» (`Draw.seedPlayers`), пустая до этого момента.

### Форма регистрации (`Forms.gs`)
`FormsService.createRegistrationForm` — добавляется обязательный
`addListItem()` «Пол» со значениями `["Мужской", "Женский"]`, сразу после
поля «Дата рождения».

### Импорт (`Participants.gs`)
`mapFormColumns` / импорт из Excel — добавляется маппинг колонки «Пол»
(обязательное поле; при отсутствии в исходных данных — импорт участника
пропускается с пометкой в результатах, как остальные некорректные
строки сейчас).

### Тестовые данные (`Testing.gs`)
`generateTestParticipants` уже вычисляет `isMale` для ФИО/отчества —
дополнительно пишет `"Мужской"`/`"Женский"` в новую колонку.

### Конфиг турнира (`Config.gs`)
`TournamentConfig`: новое поле `mixedTournament` (boolean, **default
`true`**). `ConfigService.save/load` — новая строка «Смешанный турнир»
(`"Да"`/`"Нет"`).

**Обратная совместимость**: значение по умолчанию `true` воспроизводит
сегодняшнее поведение (единая сетка на всех). Существующие таблицы,
где строка «Смешанный турнир» в «Настройках» отсутствует, трактуются как
`true` (см. `ConfigService.load` — поле остаётся `true`, если строка не
найдена, т.к. `TournamentConfig` конструктор уже проставляет `true` по
умолчанию, а `load` не перезаписывает поля, для которых нет строки в
листе).

### Границы категорий и порог слияния (константы, не в UI)
В `Config.gs`, рядом с `CONFIG`:
```js
const AGE_CATEGORIES = {
  CHILD: { label: "Дети", maxAge: 12 },
  TEEN:  { label: "Подростки", maxAge: 17 },
  ADULT: { label: "Взрослые", maxAge: null } // без верхней границы
};
const CATEGORY_MERGE_THRESHOLD = 4;
```

## 2. Мастер настройки (`Wizard.gs`)

После шага «Тип турнира» (`matchType`) добавляется:
```js
const mixedTournament = this.askChoice(ui, "Смешанный турнир?",
  { YES: "Да — общая сетка на всех", NO: "Нет — разделить по возрасту и полу" },
  cfg.mixedTournament === false ? "NO" : "YES");
if (mixedTournament === null) return null;
cfg.mixedTournament = mixedTournament === "YES";
```
Никаких дополнительных вопросов (границы возраста, порог) мастер не
задаёт — это константы.

## 3. Модуль категоризации — новый файл `Categories.gs`

Чистая логика, не трогает лист напрямую (пишет вызывающая сторона —
`Draw.seedPlayers`), чтобы было легко проверить вручную через
`Testing.gs`-подобный ран.

```
class Categories {
  static assign(participants, mixed): Map<participantId, categoryLabel>
}
```

Алгоритм `assign`:
1. Если `mixed === true` — все участники получают категорию `""`
   (пустая строка = «без категории»; весь нижестоящий код,
   зацикленный по категориям, при пустом множестве категорий делает
   ровно один проход с фильтром "все участники" — то есть ведёт себя
   как сегодня).
2. Иначе — для каждого участника считается `age` (уже есть
   `Participants.calcAge`) и по `AGE_CATEGORIES` определяется базовая
   возрастная группа (Дети/Подростки/Взрослые), затем корзина
   `{возрастная группа}×{пол}` — итого до 6 корзин.
3. **Слияние, шаг 1 (убрать пол)**: для каждой из 3 возрастных групп —
   если хотя бы одна из её гендерных корзин (М или Ж) содержит меньше
   `CATEGORY_MERGE_THRESHOLD`, обе гендерные корзины этой возрастной
   группы объединяются в одну безгендерную корзину с меткой
   `{возрастная группа}` (например, "Подростки").
4. **Слияние, шаг 2 (соседний возраст)**: после шага 1 остаются от 1 до
   6 корзин, каждая либо безгендерная (после слияния), либо
   гендерная (если обеих полов хватило). Для любой корзины, где всё ещё
   меньше `CATEGORY_MERGE_THRESHOLD`, выполняется слияние со старшим
   возрастным соседом (Дети → в Подростки, Подростки → в Взрослые);
   если малая корзина — «Взрослые» (старшего соседа нет), она сливается
   с младшим соседом («Подростки», а если и тот уже был поглощён — с
   тем, что от него осталось). Если после слияния итог всё ещё меньше
   порога — процесс повторяется рекурсивно на оставшихся корзинах, пока
   не наберётся порог или не останется одна общая корзина «Все».
   - Если сливаются корзины разной "гендерности" (одна уже безгендерная,
     другая ещё гендерная) — результат безгендерный (гендерная корзина
     теряет разделение).
5. Метки категорий генерируются по итоговому составу: чистая
   возрастная группа без слияния → её `label` ("Дети"); та же группа с
   гендерным разделением → `"{label} (М)"` / `"{label} (Ж)"`; слияние
   двух и более возрастных групп → диапазон, например "Дети и
   подростки" (Дети+Подростки), "Все" (если слились все три).

Результат передаётся в `Draw.seedPlayers`, который пишет колонку
«Категория» в лист «Участники» одновременно с посевом.

## 4. Конвейер жеребьёвки и матчей

`Draw.gs` / `Matches.gs`: следующие статические методы получают
параметр `category` (строка — метка категории, `""` при `mixed=true`) и
работают только с участниками/группами/матчами этой категории:
`createGroups`, `getSeededParticipants`, `generateGroupMatches`,
`startSingleElimination`, `startSwissRound1`, `startSwissNextRound`,
`startDoubleElimination`, `advancePlayoffIfReady`,
`tryGenerateNextDERounds`, `getGroupStandings`,
`computeStandingsForMatches`, `getPlayoffQualifiers`, `recalcRating`.

Вызывающая сторона (обработчики меню `menu_createGroups`,
`menu_startSwiss`, `menu_startSingleElimination`,
`menu_startDoubleElimination` и т.д. в `Menu.gs`) получает список
активных категорий (`Categories.activeLabels()` — уникальные значения
из колонки «Категория» листа «Участники», либо `[""]` при
`mixed=true`) и вызывает соответствующий метод `Draw`/`Matches` в
цикле по каждой категории. Ошибка в одной категории (например,
недостаточно участников для выбранной системы) не должна прерывать
обработку остальных — собирается сводный отчёт об успехах/ошибках по
категориям и показывается одним `ui.alert`.

### Листы
- **«Матчи»** — единственный лист, который код читает обратно по
  колонкам (`MATCH_COL`). Категория добавляется **последней колонкой**
  (16-й), не первой: так меняется только сам `MATCH_COL` (добавляется
  `CATEGORY: 16`), а не сдвигаются индексы всех существующих полей —
  это сильно меньше риска при правке ~15 мест, где код собирает строку
  матча литералом. Каждое место, создающее строку в «Матчи», добавляет
  категорию последним элементом массива.
- **«Группы» и «Плей-офф»** — это чисто отображающие листы (программно
  никогда не читаются обратно по категориям — жеребьёвка берёт данные
  из «Участники», итоги групп/сетки — из «Матчи»), поэтому отдельная
  колонка им не нужна. Вместо колонки — секция-заголовок на категорию,
  тем же приёмом, что уже используют заголовки «Группа A»/раунда:
  жирная строка с названием категории перед её группами/сеткой.
- Имена групп внутри категории остаются буквенными (A/B/…) как сейчас.
  ID матчей остаются глобально уникальными сквозным счётчиком
  (`Draw.getNextMatchId`), как сейчас — категория не входит в ID.

### Важное ограничение реализации: листы, которые каждый вызов ПЕРЕЗАПИСЫВАЕТ целиком
`writeGroupsSheet`, `Matches.recalcRating` и лист «Плей-офф» внутри
`startSingleElimination` делают `sheet.clear()` и пишут заново с нуля.
Если вызвать такую функцию в цикле по категориям (как в наивном
прочтении раздела «конвейер» выше) — каждый следующий вызов сотрёт
результат предыдущей категории, и на листе останется только последняя.
Поэтому у функций, которые ОЧИЩАЮТ лист (`Draw.createGroups`,
`Draw.startSingleElimination`, `Matches.recalcRating`), цикл по
категориям — ВНУТРИ самой функции: один `clear()`, затем один проход
записи со всеми категориями подряд (секциями). У функций, которые
только ДОБАВЛЯЮТ строки (`generateGroupMatches`→«Матчи»,
`startSwissRound1`/`startSwissNextRound`, `startDoubleElimination`,
`advancePlayoffIfReady`, `tryGenerateNextDERounds`, `appendToPlayoffSheet`)
— порядок цикла (внутри или снаружи функции) на корректность не влияет,
но для единообразия интерфейса он тоже остаётся внутри: вызывающая
сторона (обработчики меню) везде видит один вызов, возвращающий сводку
по всем категориям, а не думает о цикле сама.

### Разрешение категории для пар (`Teams.gs`)
Строка пары в «Участники» не хранит дату рождения/пол (неприменимо для
составной записи) — собственных данных для вычисления категории у неё
нет. `Categories.assign` разрешает это так: для строки-пары (есть «ID
участника 1») возраст/пол берутся из строки участника 1 в общем
(нефильтрованном) списке листа «Участники» — даже притом что сама эта
строка исключена из посева статусом «В паре». Обычные одиночные
участники продолжают использовать собственные дату рождения и пол.

### Столы и очередь матчей
`Matches.startNextMatch` / `pickTable` — общий пул столов
(`config.tables`) на все категории одновременно, следующий неигранный
матч выбирается по всей очереди без учёта категории (дети и взрослые
играют на одних и тех же столах по мере освобождения) — логика выбора
стола не меняется.

## 5. Отчёты (`Reports.gs`)

Лист «Рейтинг» (после раздела 4 — теперь секционирован по категориям,
как «Группы»/«Плей-офф») читается обратно функцией `getStandings(ss)` —
она меняется, чтобы возвращать список с полем `category` у каждой
строки (парсит секционные заголовки так же, как `writeGroupsSheet`
пишет их).

Финальный протокол (`menu_finalProtocol`) и дипломы
(`menu_generateDiplomas`) формируются отдельно на каждую категорию:
призовые места (1/2/3) считаются внутри категории (группируют
`getStandings()` по `category` перед построением таблиц/дипломов), а
не по турниру в целом. При `mixed=true` (одна пустая категория) вывод
не отличается от текущего — просто одна безымянная секция.

## 6. Парные турниры (`Teams.gs`)

Категория пары = категория первого участника пары (`ID участника 1`).
Пол второго участника пары на совпадение не проверяется — организатор
сам следит за корректностью состава пары при парном турнире с
разделением по категориям.

## Тестирование

В проекте нет автоматической тестовой обвязки для `.gs`-кода (только
`Testing.gs` для ручной генерации данных). Проверка — вручную через
Apps Script редактор:
1. `Testing.generateTestParticipants(N)` — расширить, чтобы явно
   покрывать пограничные случаи (участники ровно на границе 12/13 и
   17/18 лет, и категории на грани порога слияния — 3 и 4 человека).
2. Ручной прогон: `mixed=false`, посев → проверить колонку
   «Категория» и корректность слияний по алгоритму из раздела 3.
3. Прогон группы→плей-офф на многокатегорийных тестовых данных,
   финальный протокол — проверить, что призовые места считаются
   отдельно по категориям.
4. Регрессия: тот же прогон с `mixed=true` (или без строки «Смешанный
   турнир» в старой таблице) — сравнить с поведением до изменений,
   убедиться, что ничего не сломалось для однокатегорийных турниров.

## Вне рамок

- Настройка границ возраста/порога слияния через UI — не делаем,
  константы в коде.
- Проверка соответствия пола игроков в паре — не делаем.
- Отдельные комплекты листов на категорию (подход B из обсуждения) —
  отклонён в пользу тега «Категория» в общих листах.
